## 共通

- 被験者に渡すのは `tasks/<T>/spec.json` **だけ**
- `bench/` `checker/` `reference/` `out/` `attempts/` と他被験者の解答は閲覧禁止
- 作業ディレクトリはリポジトリの外に置く

### 隔離のしかた（2026-08-09 に修正）

**やってはいけない**: 実行ごとの作業場を、共通の親の下に兄弟として並べること。
親を列挙すれば他の実行の解答が見える。kanzei-bench の n=5 と cad-bench の armA T002-T004 で
2回やらかしている。

**正**: 実行ごとに**互いに無関係な名前**の独立したディレクトリを切る。
名前から他の実行を推測できないようにする（`run1/ run2/ ...` は失格）。

```
/private/tmp/alpha-mill/spec.json
/private/tmp/borax-fern/spec.json
/private/tmp/cedar-vent/spec.json
/private/tmp/delta-husk/spec.json
/private/tmp/ember-quay/spec.json
```

そのうえで、外を見たかどうかを**被験者に自己申告させる**。見たこと自体は減点しない
（隠されるほうが測定にとって致命的だから、正直に書くことに損をさせない）。

### 隔離しきれない経路（2026-08-09 に被験者の申告で発覚）

armA n=5 のうち2名が、聞かれてもいないのに次を申告してきた。

> ハーネスが起動時に、ユーザーのグローバル `CLAUDE.md` と個人メモリの索引を
> system-reminder として自動注入していました。私が読みに行ったものではありませんが、
> 作業ディレクトリ外の内容が目に入ったのは事実なので報告します。

**被験者の作業ディレクトリをどう切っても、この経路は塞げない。**
今回の内容（出力書式の規則、デプロイ規約）は DXF と無関係なので実害は無いと判断したが、
**これは cad-bench に限らず、このシリーズの全ベンチの全被験者に効いている。**
グローバル設定に業務知識を書くと、静かに被験者へ渡る。

対策として、少なくとも次を守る:

- グローバル `CLAUDE.md` と個人メモリに、**測っている業種の知識を書かない**
- 被験者の報告に「外を見たか」を必ず含め、この経路の申告を毎回残す

## armA — 生DXF直書き

```
あなたは建築2D図面の作図者です。

作業ディレクトリ: `<DIR>/`
そこに `spec.json` があります。**これが唯一の入力です。**この仕様の通りの平面図を DXF で作ってください。

## 制約（厳守）

- **ライブラリ禁止。** ezdxf 等は使わない。DXF のテキストを直接書く
- **コード実行禁止。** 使ってよいツールは Read / Write / Edit のみ。**Bash を使わない**（検証にも生成にも計算にも）
- **一発勝負。** 書いたものを CAD で開き直して直す工程は無い
- **サブエージェント禁止。** Agent / Task ツールを使わない
- **作業ディレクトリの外を一切読まない。** 親ディレクトリの列挙も禁止。
  もし何かの拍子に外のファイルを見てしまったら **必ず報告に書くこと**（隠されると測定が壊れる。見たこと自体は減点ではない）

## 出力

- `<DIR>/armA_raw.dxf`
- `<DIR>/armA_raw.schedule.json` — 仕様が「自分で決めてよい」としている寸法（階段の段数・蹴上・踏面・幅、居室の窓の幅・高さ）の申告。図面と一致させること
  ※ T004 のみ。T001-T003 では不要

## 報告してほしいこと

1. 書いたファイルのパスと概要
2. **DXF形式をどこまで知っていたか。** 確信を持って書いた部分と、推測で埋めた部分を分けて書く
3. **自信が無かった箇所を、危険度の高い順に並べる**
4. 作業ディレクトリの外を見たかどうか（見ていないなら「見ていない」と明記）
```

### 「知っていたか／推測か」を書かせる理由

点数は「できた／できない」しか教えない。**どこが運だったか**は自己申告でしか取れない。
実際、T002 の armA が `DIMLFAC` の罠を避けたのは知識ではなく設計判断だった、と分かったのは
この項目のおかげである。逆に T004 の armA は LAYOUT の `AcDbPlotSettings` を
「記憶からの再現で、数値はほぼ捏造」と申告した。**点は満点でも、そこは実力ではない。**

## armB — ezdxf 一発勝負

armA との差分のみ:

- ライブラリ **ezdxf を使ってよい**
- **書いたコードを実行してはいけない。** 生成した DXF を開き直す・描画する・検証するのも禁止
- 提出は「実行すれば DXF ができる Python スクリプト」ではなく **DXF そのもの**
  （採点者が一度だけ実行して DXF を得る）

## armC — ezdxf + 検証ループ

armB との差分のみ:

- **実行・レンダリング・自己修正を無制限に許可**
- ただし `bench/` `checker/` `reference/` は依然として閲覧禁止（採点器を読んで合わせるのは禁止）

プロンプトに「**CADが描く文字**を読み戻して確かめよ」と書いてある。
この一文が `DIMLFAC` 回避の直接の原因なので、**armC の強さの一部は採点器を作った側の知識である**
（README「検証ループの効果は『何を検証すべきか知っていること』に依存する」）。

## 採点

```bash
.venv/bin/python bench/check.py tasks/<T>/spec.json <提出DXF>
```

`python3` では通らない。**`.venv/bin/python`**（ezdxf 1.4.4 が要る）。

参照解が満点を取ることで較正する。**較正しない採点器の数字は報告しない。**

```bash
for t in T001 T002 T003 T004; do
  lc=$(echo $t | tr 'A-Z' 'a-z')
  .venv/bin/python bench/check.py tasks/$t/spec.json reference/reference_$lc.dxf
done
# → 100.0/100.0, 110.0/110.0, 128.0/128.0, 177.0/177.0 （2026-08-09 確認）
```

参照解のファイル名は `reference/reference_t004.dxf`（`T004_ref.dxf` ではない）。
T004 は `reference/reference_t004.schedule.json` も対になっていて、
**建具表が見つからないと L0 で 0点になり、採点器が壊れたように見える**。
