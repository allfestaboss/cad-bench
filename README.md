# cad-bench — AIは建築2D図面をどこまで書けるか

DXF形式の建築2D図面（平面図）をAIがどこまで作図できるかを、機械採点で測るベンチマーク。

## なぜ作ったか

公開ベンチマークが存在しないから。既存のCAD生成評価は2種類しかない。

- **3D機械部品**（Text2CAD, DeepCAD, CAD-Recode, CADGenBench）— solid の妥当性、Chamfer distance、IoU を測る
- **間取りレイアウト**（RPLAN, MSD, RFP-A）— 部屋数、隣接関係、面積誤差を測る

どちらも**製図の正しさを測っていない**。寸法線も通り芯も建具符号も線種も図面枠も、評価軸に入っていない。
日本の製図作法は JIS A 0150（建築製図通則）で成文化されているので、「採点できないから測られていない」わけではない。

## 設計の核心：設計と作図を分離する

間取りを `spec.json` で完全に与える。測るのは**作図能力だけ**で、設計能力は測らない。

これで正解が spec から一意に導出でき、**非公開の実図面を必要としない**。
「作図注記つきの正解データが手に入らない」という、ベンチが作られてこなかった最大の理由を回避する。

正解の壁形状は作図者の癖ではなく原理から決める:

> 壁 = 壁芯を ±(壁厚/2) で膨らませて union した領域
> 描くべき線 = (その領域 − 開口) の**境界**

T字接合のトリムも、開口の小口（ジャンブ）も、斜め壁も、この定義から自動的に出る。

## 採点のハシゴ

| 段 | 何を問うか | 状態 |
|---|---|---|
| L0 | DXFとして開けるか | 採点 |
| L1 | 幾何が健全か（壁厚、被覆率、余計な線、レイヤ規約） | 採点 |
| L2 | 寸法が本物か（DIMENSION、作図ブロック、**表示される値**） | 採点 |
| L3 | 意味が合うか（開口の欠き込み、建具、室名、通り芯、階段） | 採点 |
| L4 | 法規に適合するか（階段の蹴上/踏面/幅、居室の採光/換気） | 採点 |
| L5 | 製図の作法（文字高さ、線種、符号の丸囲み、図面枠） | 助言のみ・点数外 |
| L6 | 実務で通用するか | 人間の判定 |

**L2 は「内部の計測値」ではなく「CADが描く文字」を見る。** ここを見落とすと、幾何が完璧で寸法だけ100倍の図面が満点になる（実際になった）。

## 実験プロトコル

被験者エージェントには `tasks/<T>/spec.json` **だけ**を渡す。
`bench/` `checker/` `reference/` `out/` と他被験者の解答は閲覧禁止。

- **armA** 生DXF直書き。ライブラリ禁止、実行禁止、一発勝負
- **armB** ezdxf で CAD-as-code。実行・検証禁止、一発勝負
- **armC** ezdxf で CAD-as-code。**実行・レンダリング・自己修正を無制限に許可**

参照解（`bench/build_ref.py`）は spec から決定論で組む。**採点器は参照解が満点になることで較正する。**
較正しない採点器の数字は、AIの実力なのか採点器のバグなのか区別できない。

## 使い方

```bash
python3 -m venv .venv && .venv/bin/pip install ezdxf shapely matplotlib
bash run.sh            # 全課題
bash run.sh T002       # 課題を指定
```

`out/<T>.txt` に詳細、`reference/*.png` `attempts/*/*.png` に描画結果。

## 課題

- **T001** 木造平屋 1階平面図。4室・開口4・寸法13本。座標は全て spec に明示（＝転記の課題）
- **T002** 木造2階建て 1階平面図。10室・開口8・寸法38本・**45度の斜め外壁とその開口**・**通り芯に乗らない455mm半モジュール壁**・**折返し階段の段板14本**。座標は全て明示
- **T004** T003と同じ建物で、**法規が支配する部分だけを自由**にする。階段（段数・蹴上・踏面・幅）と居室の窓（幅・高さ）を模型が決め、
  建具表（`<dxf>.schedule.json`）として申告し、図面にもその通り描く。申告と図面が食い違えば壁の被覆率が落ちる。
- **T003** T002と同じ建物を、**座標をほとんど与えずに**記述。壁も室も通り芯符号で宣言し、開口は「その室の中央に幅910」のような関係で与える。
  さらに **各室の面積・床面積合計・開口位置の寸法系統を自分で導出**させる。
  被験者には宣言的な仕様だけを渡し、採点器は `bench/resolve.py` が決定論で解決した具体仕様を使う。

### L4 は正解の図面を必要としない

L0–L3 は「正解の図面」との照合。**L4 は制約充足の検査**なので、正解が要らない。
だから L4 を入れて初めて、**設計の自由度を開いたまま採点できる**。

L4 の限界（誠実に）: 採光補正係数（令20条）を1と仮定した簡略モデルで、実務の判定には使えない。
また **窓の高さは平面図から読めない**ので、建具表の申告を信じるしかない
——これは実務で建具表と姿図が別図書として要求される理由そのもの。平面図だけでは採光は証明できない。

### 座標を書いた瞬間、それは転記の課題になる

T001・T002 では全座標を spec に書いた。LLMは転記が得意なので、これでは天井が測れない
（一発勝負の armB でも T002 は 105/110）。難しさの本体は座標の個数ではなく、**拘束の相互作用と導出**にある。
T003 はそこを測るために作った。

## 実験の統制について（正直な記録）

T002 のプロンプトには、T001 で判明した2点（「T字接合を通すな」「1:100で紙に刷る前提」）を書き込んだ。
仕様として正しい追記だが、その結果 T002 で `DIMLFAC` の誤用が起きなかったのが**能力なのかヒントなのかは n=1 では区別できない**。

## 結果（n=1）

```
        参照解   armA 生DXF   armB 一発勝負   armC 検証ループ
T001     100       85.2         89.8          100.0
T002     110      欠測(529)     105.0          110.0
T003     128        —           128.0          127.9
T004     177        —           167.0          172.0     ← L4法規は両腕とも 59/59 満点
```

失敗は2系統しかない。

1. **寸法の意味論**（`DIMLFAC`を100にして表示だけ100倍 / DIMENSIONの作図ブロック欠落 / 回転角忘れ）。
   armB T001 と armB T004 で**同じ `DIMLFAC` の誤りが再現**した。法規計算は一つも間違えていないのに、
   図面には「幅910メートルの木造住宅」と印字される。**Chamfer distance も IoU も検出できない。**
2. **45度の隅のマイター**。armB(T002)、armC(T004)、そして採点器を書いた本人が落ちた。
   図面のどこを見ても正しく見えるので、**自己検証では捕まらない**。

### 検証ループの効果は「何を検証すべきか知っていること」に依存する

armC が `DIMLFAC` を回避できたのは、プロンプトに「**CADが描く文字**を読み戻して確かめよ」と書いたから。
その一文は、採点器を作って初めて書けるようになった。**検査器がないと、何を検証すべきかが分からない。**
armC は45度の隅では、何を見ればいいか知らなかったので落ちた。

## 既知の弱点

- 各課題 n=1（各腕1回）。統計になっていない
- T002 の armA（生DXF直書き）は API の 529 で途中終了。データ無し（能力の結果ではない）
- 仕様も採点器も同一人物が書いた
- L4（法規）未接続、L5 未点数化
- 立面図・断面図・編集タスク・修復タスクが無い
