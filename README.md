# cad-bench — AIは建築2D図面をどこまで書けるか

[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.21847358.svg)](https://doi.org/10.5281/zenodo.21847358)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

DXF形式の建築2D図面（平面図）をAIがどこまで作図できるかを、機械採点で測るベンチマーク。

## なぜ作ったか

公開ベンチマークが存在しないから。既存のCAD生成評価は2種類しかない。

- **3D機械部品**（Text2CAD, DeepCAD, CAD-Recode, CADGenBench）— solid の妥当性、Chamfer distance、IoU を測る
- **間取りレイアウト**（RPLAN, MSD, RFP-A）— 部屋数、隣接関係、面積誤差を測る

どちらも**製図の正しさを測っていない**。寸法線も通り芯も建具符号も線種も図面枠も、評価軸に入っていない。
日本の製図作法は JIS A 0150（建築製図通則）で成文化されているので、「採点できないから測られていない」わけではない。

## 設計の核心：設計と作図を分離する

間取りを `spec.json` で完全に与える。測るのは**作図能力だけ**で、設計能力は測らない。

これで正解が spec から一意に導出でき、**非公開の実図面を必要としない**。
「作図注記つきの正解データが手に入らない」という、ベンチが作られてこなかった最大の理由を回避する。

正解の壁形状は作図者の癖ではなく原理から決める:

> 壁 = 壁芯を ±(壁厚/2) で膨らませて union した領域
> 描くべき線 = (その領域 − 開口) の**境界**

T字接合のトリムも、開口の小口（ジャンブ）も、斜め壁も、この定義から自動的に出る。

## 採点のハシゴ

| 段 | 何を問うか | 状態 |
|---|---|---|
| L0 | DXFとして開けるか | 採点 |
| L1 | 幾何が健全か（壁厚、被覆率、余計な線、レイヤ規約） | 採点 |
| L2 | 寸法が本物か（DIMENSION、作図ブロック、**表示される値**） | 採点 |
| L3 | 意味が合うか（開口の欠き込み、建具、室名、通り芯、階段） | 採点 |
| L4 | 法規に適合するか（階段の蹴上/踏面/幅、居室の採光/換気） | 採点 |
| L5 | 製図の作法（文字高さ、線種、符号の丸囲み、図面枠） | 助言のみ・点数外 |
| L6 | 実務で通用するか | 人間の判定 |

**L2 は「内部の計測値」ではなく「CADが描く文字」を見る。** ここを見落とすと、幾何が完璧で寸法だけ100倍の図面が満点になる（実際になった）。

## 実験プロトコル

被験者エージェントには `tasks/<T>/spec.json` **だけ**を渡す。
`bench/` `checker/` `reference/` `out/` と他被験者の解答は閲覧禁止。

- **armA** 生DXF直書き。ライブラリ禁止、実行禁止、一発勝負
- **armB** ezdxf で CAD-as-code。実行・検証禁止、一発勝負
- **armC** ezdxf で CAD-as-code。**実行・レンダリング・自己修正を無制限に許可**

参照解（`bench/build_ref.py`）は spec から決定論で組む。**採点器は参照解が満点になることで較正する。**
較正しない採点器の数字は、AIの実力なのか採点器のバグなのか区別できない。

## 使い方

```bash
python3 -m venv .venv && .venv/bin/pip install ezdxf shapely matplotlib
bash run.sh            # 全課題
bash run.sh T002       # 課題を指定
```

`out/<T>.txt` に詳細、`reference/*.png` `attempts/*/*.png` に描画結果。

## 課題

- **T001** 木造平屋 1階平面図。4室・開口4・寸法13本。座標は全て spec に明示（＝転記の課題）
- **T002** 木造2階建て 1階平面図。10室・開口8・寸法38本・**45度の斜め外壁とその開口**・**通り芯に乗らない455mm半モジュール壁**・**折返し階段の段板14本**。座標は全て明示
- **T003** T002と同じ建物を、**座標をほとんど与えずに**記述。壁も室も通り芯符号で宣言し、開口は「その室の中央に幅910」のような関係で与える。
  さらに **各室の面積・床面積合計・開口位置の寸法系統を自分で導出**させる。
  被験者には宣言的な仕様だけを渡し、採点器は `bench/resolve.py` が決定論で解決した具体仕様を使う。
- **T004** T003と同じ建物で、**法規が支配する部分だけを自由**にする。階段（段数・蹴上・踏面・幅）と居室の窓（幅・高さ）を模型が決め、
  建具表（`<dxf>.schedule.json`）として申告し、図面にもその通り描く。申告と図面が食い違えば壁の被覆率が落ちる。

### L4 は正解の図面を必要としない

L0–L3 は「正解の図面」との照合。**L4 は制約充足の検査**なので、正解が要らない。
だから L4 を入れて初めて、**設計の自由度を開いたまま採点できる**。

L4 の限界（誠実に）: 採光補正係数（令20条）を1と仮定した簡略モデルで、実務の判定には使えない。
また **窓の高さは平面図から読めない**ので、建具表の申告を信じるしかない
——これは実務で建具表と姿図が別図書として要求される理由そのもの。平面図だけでは採光は証明できない。

### 座標を書いた瞬間、それは転記の課題になる

T001・T002 では全座標を spec に書いた。LLMは転記が得意なので、これでは天井が測れない
（一発勝負の armB でも T002 は 105/110）。難しさの本体は座標の個数ではなく、**拘束の相互作用と導出**にある。
T003 はそこを測るために作った。

## 実験の統制について（正直な記録）

T002 のプロンプトには、T001 で判明した2点（「T字接合を通すな」「1:100で紙に刷る前提」）を書き込んだ。
仕様として正しい追記だが、その結果 T002 で `DIMLFAC` の誤用が起きなかったのが**能力なのかヒントなのかは n=1 では区別できない**。

## 結果（armA T004 のみ n=5、他は n=1）

**満点は課題ごとに違う**（適用される検査が違い、T004 には法規の L4 が加わる）。
無理に100点へ揃えると配点を恣意的に歪めるので、**率で報告する**。
他の4業種と横断で比べられるのはこの列。

```
          満点   armA 生DXF   armB 一発勝負   armC 検証ループ
T001      100      85.2%        89.8%         100.0%
T002      110     100.0%         95.4%        100.0%
T003      128     100.0%        100.0%         99.9%
T004      177    (94.2%)         94.4%         97.2%   ← L4法規は3腕とも 59/59 満点
```

**armA T004 は n=5 の中央値**（0.0 / 94.2 / 94.2 / 100.0 / 100.0）。
他のセルはすべて n=1 で、**同じ幅で散らばっている可能性がある。**
armA T004 の初回は 100.0% だったが、それは分布の上端だった。

生点では T003 の 128 と T001 の 100 が比較できず、
「T003 で armB が満点」という事実が読み取れなかった。

### armA を n=5 で取り直したら、順位が消えた（T004）

上の表の armA は各課題1回である。T004 だけ5回取り直した。

```
run           点      行数    寸法の作図ブロック
ember-quay  100.0%   11,406   34個すべてに中身（136エンティティ）
borax-fern  100.0%   12,151   34個すべてに中身（68）
delta-husk   94.2%    9,634   34個あるが全部空
cedar-vent   94.2%    6,958   空の1個を34本で共有
alpha-mill    0.0%    6,927   ファイルが開かない

中央値 94.2%   平均 77.7%   範囲 0 – 100
```

**中央値 94.2% は armB(94.4%) と armC(97.2%) を下回る。**
最初に報告した armA T004 = 100.0% は**分布の上端であって中心ではなかった**。
5本中2本しか届いていない。

このリポジトリは「n=1 で順位を語らない」を掲げながら、
1回の 100% を見て「一番弱いはずの腕が一番強かった」と書いた。**その節は撤回した。**

#### 分かれ目は能力ではなく、どこで手を止めるか

5本の差は、**寸法の作図ブロックを書ききるかどうか**の一点にほぼ集約される。
34本の寸法に絵を付けるには 1,700 行ほど余計に打つ必要があり、
書いた2本が 100%、省いた2本が 94.2% になった。省いた側は3本とも理由を明示している。

> 34個分のジオメトリを手書きすると出力量が破綻する。DIMENSION 側に定義点を正しく持たせ、
> ブロック本体は空にした。**ezdxf で列挙・計測する採点なら通るが、CAD で開いても寸法は何も描画されない。**

**同じ模型が、同じ課題で、正反対の判断をしている。**
能力の差ではなく、締切と品質のどちらを取るかの判断がぶれている。

#### 1回に1回は、ファイルごと死ぬ

alpha-mill は 6,927 行のうち**1行**で全損した。`0` の直後に値の `0` が余分に1本入り、
次の `TEXT` がグループコードとして読まれて、そこから先のパースが全部ずれる。
診断としてその1行だけ削ると **93.9%** になる。**0点と94点の差が1行である。**

同じ欠陥は他の実行にも発生していた。違いは**見つけたかどうか**だけである。

- borax-fern: 「9回に分けて追記したので全チャンク境界を自己監査した。
  **余分な `0` 行が2箇所**あり、両方修正した。さらに各セクションの開始行を
  エンティティ数から予測し、実際の位置と一致することを確認した」→ 100.0%
- T003 の armA も同じく2箇所を自分で見つけて修正 → 100.0%
- alpha-mill は同じ粒度の監査をしていない → 0.0%

**実行環境の無い腕にとって、唯一の検証手段は自分の出力を読み返すことである。**
それをやった実行は生き残り、やらなかった実行は死んだ。

### armA が回避した罠（n=1 の観察として）

- **`DIMLFAC`**（T002 armA の自己申告）
  「DIMENSION にグループコード1を意図的に置かなかった。CAD が defpoint 13/14 から値を計算するようにして、
  自分がタイプした上書き値を表示させない。ブロック内の MTEXT にも同じ文字列を持たせたので、
  再生成する経路もしない経路も同じ数字を表示する。**どちらも私が書いた嘘ではない。**」
  罠を知らないまま、「自分の書いた値を表示させない」という設計判断だけで構造的に回避している。
- **45度のマイター** を T002・T003・T004 の3課題すべてで通した。
  armB(T002)・armC(T004)・採点器の作者が落ちた箇所である。

ライブラリを使う腕が落ちるのは、**ライブラリが「それらしい正しさ」を安く出せるから**だと読める。
`ezdxf` は `DIMLFAC` を設定させてくれるし、その結果が図面に何と印字されるかは教えない。
手書きの腕はその近道を持たないので、表示される文字まで自分で面倒を見るしかない。

ただしこれは n=1 の観察である。上の n=5 では、armA も別の形の「安い正しさ」に手を出した——
**定義点だけ正しく置いて絵を省いた空の作図ブロック**。
どの腕も、採点されないと踏んだところを削る。削る場所が違うだけである。

### ただし、採点していない層では armA が最下位である

L5（製図の作法）は点数化していない。そこだけを数えると、順位が逆さまになる。

```
                L5 不合格（5項目中）        図面枠を除く
        T001  T002  T003  T004   計        （全腕共通の失点を除いた分）
armA      3     2     3     3    11             7
armB      2     1     2     1     6             2
armC      2     1     2     2     7             3
```

「図面枠・表題欄がある」は**12提出すべてが落とした**ので腕の差ではない。
それを除くと armA だけが落とす項目が残る——**通り芯が一点鎖線**（T001, T003）と
**通り芯符号が丸囲み**（T002, T004）。どちらも行数を食う作法である。
丸囲みは円が21個要る。ライブラリならループ1行、手書きなら21エンティティを打つ。
LTYPE のパターン定義も同じで、armA T004 は「ACADの出荷パターンを記憶から再現して×50した」と申告している。

**手書きの腕は、高くつく作法を落としている。**
そして落とした先が、たまたま点数化していない層だった。

だから「armA が最強」は**測る層を我々が選んだ結果**でもある。
L5 を点数化すれば順位は変わる。L5 を点数化していないのは、
JIS A 0150 の解釈を採点器に固定する自信が無かったからで、能力の話ではない。

### armA のリスクは一点に集中している

T003 の armA はこう報告した。

> 実際に重複 `0` 行を2箇所やらかしており、13,000行を grep も検証もできない条件下では、
> 同種のタイプミスが1つでも残っていればファイル全体が死ぬ。これが圧倒的に最大リスク。

自分でその2箇所を見つけて直したから満点になった。見逃していれば 0 点である。
**armA の点は高いが、分散は測っていない**（n=1、下の「既知の弱点」）。

失敗は2系統しかない。

1. **寸法の意味論**（`DIMLFAC`を100にして表示だけ100倍 / DIMENSIONの作図ブロック欠落 / 回転角忘れ）。
   armB T001 と armB T004 で**同じ `DIMLFAC` の誤りが再現**した。法規計算は一つも間違えていないのに、
   図面には「幅910メートルの木造住宅」と印字される。**Chamfer distance も IoU も検出できない。**
2. **45度の隅のマイター**。armB(T002)、armC(T004)、そして採点器を書いた本人が落ちた。
   図面のどこを見ても正しく見えるので、**自己検証では捕まらない**。

### 検証ループの効果は「何を検証すべきか知っていること」に依存する

armC が `DIMLFAC` を回避できたのは、プロンプトに「**CADが描く文字**を読み戻して確かめよ」と書いたから。
その一文は、採点器を作って初めて書けるようになった。**検査器がないと、何を検証すべきかが分からない。**
armC は45度の隅では、何を見ればいいか知らなかったので落ちた。

## この穴は本当に空いているのか（潰しにいった記録）

- **Autodesk 公式**が「表示値が実長と一致しない原因＝`DIMLFAC` / テキスト上書き」を文書化している。
  しかし自動検出は無い。`DIMREASSOC` も `QSELECT` も手動起動で、手打ち上書きしか捕まえず、`DIMLFAC` は構造的に見逃す。
- **千葉県 照査項目チェックリスト**（[千葉県県土整備部](https://www.pref.chiba.lg.jp/)。再配布可否が未確認のため本リポジトリには同梱していない）は、図面間整合・計算書照合・数量照合を要求する。
  しかし「CAD」「自動」「ソフト」「表示値」の出現は **すべて0件**。人が紙に有／無を書く様式。
  **照査項目チェックリストが、そのまま spec.json だった。**
- **buildingSMART IDS** は Solibri の原文で "IDS currently does not have the capabilities to define intrinsic details of geometry."
- **AI生成CADの評価研究**は Chamfer / IoU / F1 / invalidity rate のみ。寸法ラベルの意味論を測る指標が無い。
- **Dessia (dessia.io)** は実在する唯一の 2D図面自動検査プレイヤー。
  図面 × BOM × 表題欄 × タグ位置 の整合は**既に商品**。ただし寸法チェーン検査は印字値どうしを足すだけで、
  `DIMLFAC=100` の図面を満点で通過させる（`checker/dessia_probe.py` で実証）。

> AIはもうCADを描ける。図面の中の「数字どうし」を照合する商品はある。
> しかし「数字と線」を照合するものは、まだどこにもない。

## 既知の弱点

- **armA T004 以外は n=1。統計になっていない。**
  唯一 n=5 を取った armA T004 は 0.0 / 94.2 / 94.2 / 100.0 / 100.0 と 100点幅で散った。
  **他の11セルも同じ幅で散っている可能性がある**ため、表から腕の順位を読んではいけない。
  n=1 の armB / armC を armA の中央値と比べるのも、厳密には成立しない
- **armA の 5本のうち1本は「no Bash」規約を1回破った**（自分の出力に対する `grep` 1回、読み取りのみ）。
  Read でも同じ検査ができるので能力上の利得はゼロと判断して採用したが、記録しておく。
  その実行は 100.0%
- **armA T001 と armA T002-T004 は同じ日に走っていない。**
  T001 は初回、T002-T004 は採点器と他腕の結果が出そろった後に発注した。
  プロンプトの文面は同じだが、**課題文（spec.json）は T001 の知見を反映して改訂されている**ため、
  85.2% → 100.0% の差を能力差として読んではいけない
- **armA T002-T004 の作業場は `/private/tmp/cad-arms/` の兄弟ディレクトリだった。**
  親を列挙すれば他課題の spec と（先に終わった腕の）DXF が見えた。
  互いに別課題なので答えの流用にはならないが、**DXF の書式そのものを参照できた可能性は排除できない**。
  「記憶からどこまで DXF を書けるか」の測定としては上振れの疑いが残る（kanzei-bench と同じ失敗）
- 仕様も採点器も同一人物が書いた
- **L5（製図の作法）は未点数化。ここを点数化すると腕の順位が変わる**（上の表）。
  点数化していないのは JIS A 0150 の解釈を採点器に固定する自信が無かったからで、
  「重要でないから」ではない。図面枠・表題欄は12提出すべてが落としている
- L4 は採光補正係数を1と仮定した簡略モデル。実務の判定には使えない（上記「L4 の限界」）
- 立面図・断面図・編集タスク・修復タスクが無い

## 関連研究 — この位置づけ

| 研究 | 対象 | 本ベンチとの違い |
|---|---|---|
| [AECV-Bench](https://api.emergentmind.com/topics/aecv-bench) | 建築・工学図面の多モーダル**理解** | 本ベンチは**作図**。図面を読むのではなく、DXF を書かせて機械採点する |
| [BIM-Edit](https://arxiv.org/abs/2606.20146v1) (2026) | IFC の自然言語編集。324タスク | 建築BIM。2D図面の作図は扱わない |
| AI生成CADの評価研究 | Chamfer / IoU / F1 / invalidity rate | 幾何の一致のみ。**寸法ラベルの意味論**を測る指標が無い |

本ベンチの位置は「**寸法の意味論まで含めて2D図面を書かせ、機械で採点する**」。
図面理解のベンチは 2026 年に入って増えているが、生成側で寸法表示値と実長の整合まで
問うものは、調査した範囲では見つからなかった（2026-08 時点）。

なお**コストを併記すること自体は 2026 年時点で標準的**であり、本ベンチの新規性ではない。
シリーズとして測っているのは、業界をまたいで条件を揃えたときの**単価の差**のほうである。
